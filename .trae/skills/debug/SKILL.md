# 调试（Debug · 察鼎辨失）

> 守城野战知凶吉，增得灵砂满鼎红。——《悟真篇》

调试如察鼎：先稳住现状，再追根因，知其凶吉才敢动手。

术的第二角度：从症状一路追到根因，修复，并验证修对了。

调不准的调，只是把症状换了个地方。思诚在这里落地：不猜测，先取证。

## 流程

1. **复现** —— 先稳定复现。复现不了的 bug，先修现路径。
2. **读错误** —— 错误信息、堆栈、日志是证据。先读全，不急着改。
3. **二分** —— 把范围切成两半——前端/后端、入参/出参、新代码/旧代码——找到第一个不符合预期的点。
4. **定位根因** —— 那个「假设它对的，但它不对」的点。写下来：根因是什么，证据在哪。
5. **修复** —— 最小改动修根因，不修症状。
6. **验证** —— 原 bug 不再现 + 相关路径不回归。验证方式写进结果。

## 纪律

- **区分假设与事实**：`?` 是猜测，`✓` 是有证据的结论。调试全程标注。
- **不做无罪假设**：先怀疑自己刚写的代码，再怀疑框架/环境。
- **一次只改一个变量**：多改多猜，谁也说不清是谁修好的。
- **保留诊断**：修复后把根因和证据写进结论（供观照沉淀 lesson）。

## 何时启用

- 用户说「报错了」「崩了」「不工作」「行为不对」「测试挂了」
- 错误信息出现但原因不明
- 修改后出现回归

## 何时不启用

- 错误一眼可读且改法明确：直接修，不进调试流程
- 是需求问题不是代码问题（行为对但需求错）：回 dao/design

## 与术层其他角度协作

- 修复涉及结构混乱 → 先 refactor 再修，或修完即重构
- 修复后 → 路由 test 补回归测试，防止复发
- 根因是设计缺陷 → 回 design，修的不该只是这一处

调试是术对「真」的实践：一次根因修复，胜过十次症状掩盖。

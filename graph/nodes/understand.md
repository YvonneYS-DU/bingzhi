# Understand Node — 理解节点

## 干什么

读懂代码改动。分两步：

### 改前（建基线）

改动前，记录当前状态：

```text
1. 列出要改的文件
2. 读关键文件，理解当前逻辑
3. 记录：这是什么、现在怎么工作的
```

输出格式：

```text
## 改前基线

### 涉及文件
- src/foo.py：负责 xxx 逻辑
- src/bar.py：xxx 的调用方

### 当前行为
foo() 做 A，然后返回 B。bar() 调用 foo() 后做 C。

### 改动目标
要让 foo() 同时支持 D 场景。
```

### 改后（确认改动）

改动后，确认实际改了什么：

```text
1. 看 diff，逐文件理解改动
2. 判断影响范围（哪些地方会受影响）
3. 输出：改了什么、为什么改、影响谁
```

输出格式：

```text
## 改动确认

### 改了什么
- src/foo.py L42-58：新增参数 `mode`，支持 D 场景
- src/bar.py L23：传入 `mode="D"`

### 为什么改
用户需要 foo() 在 D 场景下走不同逻辑。

### 影响范围
- foo() 的调用方 bar() 已更新参数
- 其他调用方不受影响（默认参数保持兼容）
```

## 不做的事

- 不猜测用户意图
- 不创造概念（"这是策略模式的变体"之类的）
- 不评价改动好坏
- 只描述代码层面的事实

## 核心规则

```text
说清楚三件事：改了什么、为什么改、影响了谁。
用中文说人话，不用术语包装。
```

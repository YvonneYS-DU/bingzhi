# 审查（Review · 防危虑险）

> 到此金砂宜沐浴，若还加火必倾危。——《悟真篇》

丹到金砂该沐浴温养，再加火必倾危。审查就是交付前的那一次停火：先把险处看穿。

术的第四角度：在交付前替代码把一遍关，找出会在将来咬人的问题。

观照在这里落地：审查是回看别人的（或自己过去的）实现，把问题在变成事故前挑出来。

## 流程

1. **先读意图** —— 这次改动想干什么？对照需求/设计，确认改对了东西。
2. **通读实现** —— 按数据流读，不只按 diff 读。看真实路径，不看孤立片段。
3. **按风险清单过** ——
   - 正确性：边界、空值、竞态、类型转换
   - 安全：输入校验、注入、权限、敏感信息
   - 性能：循环里的重活、重复计算、N+1
   - 可维护：命名、重复、函数过长、魔法数字
   - 一致性：是否符合项目 invariants / 既有风格
4. **分级反馈** —— 必改（会出事的）/ 应改（明显更优）/ 建议（风格）。不混级，不吹毛求疵。
5. **结算** —— 明确说「可合并」或「改完这几点再合并」，不带模糊态度。

## 纪律

- **按证据说话**：说问题给出处（行号/调用链/复现路径），不空说「感觉不对」。
- **先找大问题**：正确性 > 安全 > 性能 > 风格。别被小瑕疵占满注意力。
- **不做无罪推断**：默认每行都可能是错的，被证据说服才放行。
- **审查不代写**：指出问题，不改代码。改是实现的职责。

## 何时启用

- 用户说「review 一下」「看看有没有问题」「帮我把把关」
- 合并/交付/上线前
- 长任务收尾，作为质量闸门
- 接手不熟悉代码前快速摸风险

## 何时不启用

- 一步可核验的小改：直接看，不走完整审查
- 用户只想要解释代码（理解）：那是直读，不是审查

## 与术层其他角度协作

- 发现问题 → 回 implement 修，或 debug 追根因
- 结构性问题成片 → 建议 refactor
- 审查结论值得记住 → 供观照沉淀 lesson

审查是术的闸门：让「能跑」和「能交付」之间有一道明确的坎。

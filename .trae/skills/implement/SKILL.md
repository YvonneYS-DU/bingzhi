# 实现（Implement · 炼己持真）

> 人人本有长生药，自是迷徒枉摆抛。——《悟真篇》

写代码如炼己：答案本来就在心里，实现不是创造，是把它诚实地唤出来。炼的是「持真」——不糊弄、不侥幸、不代偿。

术的第一角度：把明确的需求变成可读、可测、可维护的代码。

不替用户决定「做什么」，只负责「怎么把做的东西写对」。

## 流程

1. **确认意图** —— 需求里的「是什么」和「不是什么」都点清。没确认前不动手。
2. **找落点** —— 这个改动放在哪个文件、哪个模块、哪个函数？先读现有代码，不空写。
3. **选型** —— 用项目已有模式，不引新依赖。除非需求明确要求。
4. **写实现** —— 小步写。一个改动一次验证，不一口气堆完。
5. **对照验证** —— 写完回读需求，确认行为一致、命名一致、边界处理一致。

## 纪律

- 命名服从项目既有风格（见 invariants / PREFERENCES），不发明新风格。
- 不改没读过的代码。要改先读，读不完就承认「这里我没看全」。
- 不做需求之外的事：不顺手重构、不顺手加功能。
- 不确定的接口、行为、副作用，标注 `?`，让测试或审查去结算。

## 何时启用

- 用户说「写一下」「实现」「加个功能」「做个页面/接口/脚本」
- 需求已明确（或够明确到可以动手并标注不确定处）
- 从设计角度产出结构之后，进入落地

## 何时不启用

- 需求本身模糊：先回到 dao/design 分类，不猜着写
- 只是改个配置、看个文件：直接做
- 要改的是行为而非结构，且已有测试在跑：先看 test 角度

## 与术层其他角度协作

- 写之前复杂 → 路由 design
- 写完要证明对 → 路由 test
- 写完交付前 → 路由 review
- 写完发现代码已烂 → 路由 refactor

实现是术的入口：大部分工程任务从这里开始，也在这里收尾。

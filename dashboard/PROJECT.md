# 智能会议室预定系统

> 创建日期：2026-07-01
> 最后更新：2026-08-02

## 项目是什么

一个内部使用的会议室预定系统。员工可以在 Web 上查看会议室空闲时间、预定、取消预定。管理员可以管理会议室资源。

## 解决什么问题

公司有 12 间会议室，当前靠行政小姐姐用 Excel 管理。每周一早上群里抢会议室，重复预定、超时占用、找不到空会议室是常态。

## 技术边界

### 用什么

| 层 | 选型 | 原因 |
|----|------|------|
| 前端 | React + Ant Design | 内部系统，AntD 组件齐全，开发快 |
| 后端 | Python FastAPI | 团队主力语言，异步支持好 |
| 数据库 | PostgreSQL | 会议室预定有并发冲突，需要行级锁 |
| 部署 | Docker Compose | 内网部署，不需要 K8s |

### 不用什么（及原因）

| 不用的技术 | 原因 |
|-----------|------|
| MongoDB | 预定数据有强事务需求 |
| GraphQL | 前端需求简单，REST 够用 |
| Redis | v1 先不做缓存，量不大 |
| WebSocket | v1 不做实时推送，先轮询 |

## 初始探索

项目启动时看了三种方案：

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| 自研 | 完全定制 | 开发周期长 | **采用** |
| 钉钉会议室 | 现成的 | 不支持公司的 LDAP 登录 | 不采用 |
| Cal.com 开源版 | 功能全 | 定制成本高，和公司 IT 体系不兼容 | 不采用 |

### 为什么选择自研

钉钉会议室不支持 LDAP，Cal.com 定制成本超过自研。12 间会议室的场景足够简单，自研 2 周可以出 v1。

## 第一版边界设计

```
[员工] → React 前端 → FastAPI 后端 → PostgreSQL
                              ↓
                         LDAP 认证
```

### 明确的边界

- 前端只管展示和表单，不做业务逻辑
- 后端负责预定冲突检测（数据库行级锁）
- LDAP 认证通过公司现有中间件，不自己实现

### 第一版不做的

- 不做移动端（v1 只做 PC Web）
- 不做会议室设备管理（投影仪、视频会议等）
- 不做数据分析面板
- 不做邮件/钉钉通知（v1 用户自己记住时间）

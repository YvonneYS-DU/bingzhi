## 为什么新需求不是旧需求的延续

这是给领导看的关键部分。

### R02 和 R01 的差异

```
R01 做了什么：基本的预定流程（选时间→预定→查看→取消）
R02 要做什么：管理后台 + 重复会议

为什么 R02 不是 R01 的继续修改：
- 原因1：管理后台引入了权限系统（普通用户/管理员），需要全站改造
- 原因2：重复会议涉及批量事务处理，和单次预定的逻辑完全不同

所以 R02 是独立的新需求，需要新的开发和测试。
```

### R03 和 R02 的差异

```
R02 做了什么：管理后台 + 重复会议
R03 要做什么：邮件通知 + 单次修改重复会议

为什么 R03 不是 R02 的继续修改：
- 原因1：邮件通知需要引入 Celery + Redis 异步基础设施，和 R02 的功能无关
- 原因2：单次修改需要新增 booking_exceptions 表，数据模型有变化

所以 R03 是独立的新需求。
```

### R04 和 R03 的差异

```
R03 做了什么：邮件通知 + 单次修改
R04 要做什么：数据看板

为什么 R04 不是 R03 的继续修改：
- 原因1：数据看板需要聚合查询和图表，是全新的模块
- 原因2：和 R03 的邮件系统没有任何代码复用

所以 R04 独立评估和实施。
```

## 部署建议

### v1 部署

| 注意项 | 说明 |
|--------|------|
| 数据库变更 | 首次部署，执行 init_db.sql 创建表 |
| 配置变更 | 需要 LDAP 地址、端口、Base DN |
| 依赖变更 | docker-compose up 自动拉取镜像 |
| 回滚方案 | v1 首次部署，回滚即关闭服务 |

### v2 部署

| 注意项 | 说明 |
|--------|------|
| 数据库变更 | 执行 alembic upgrade head 添加 permissions 字段 |
| 配置变更 | 无新增配置 |
| 依赖变更 | 无新增依赖 |
| 回滚方案 | alembic downgrade -1 回到 v1 schema |

### v3 部署

| 注意项 | 说明 |
|--------|------|
| 数据库变更 | 新增 booking_exceptions 表 |
| 配置变更 | 新增 SMTP_HOST, SMTP_PORT, REDIS_URL 环境变量 |
| 依赖变更 | 新增 Celery, Redis，docker-compose.yml 新增 worker 和 redis 容器 |
| 回滚方案 | 停止 worker 容器，alembic downgrade -1，去掉 REDIS_URL 配置 |
